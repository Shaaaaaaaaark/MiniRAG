# 云网络 Oncall 告警处理手册

本手册面向云网络团队 Oncall，覆盖 Transit Router、CloudWAN、VPC、专线等核心组件的高频告警。
每个条目遵循“期望态 vs 实际态”模型：先给出资源应处的正常状态，再对照实际观测到的异常，最后给出排查与处置步骤。

## Transit Router BGP 邻居中断

### 告警说明
告警名 `TR_BGP_SESSION_DOWN`，由 Transit Router 上报。当 Transit Router 与云企业网 CEN 或本地网关之间的 BGP 邻居会话从 Established 跌落时触发。

### 期望态
BGP 邻居会话状态应为 Established，且 `bgp_session_uptime` 持续增长。路由表中应包含对端通告的动态路由，`received_routes` 数量与对端通告一致。

### 实际态
实际态为 BGP 会话状态变为 Idle 或 Active，`bgp_session_uptime` 归零，`received_routes` 骤降为 0，跨地域业务流量中断。伴随指标 `bgp_neighbor_state` 从 1 变为 0。

### 常见根因
1. 对端设备重启或维护，导致 TCP 179 端口连接被重置，错误码 `BGP_HOLD_TIMER_EXPIRED`。
2. Transit Router 路由条目数超过配额 `route_limit`（默认 10000 条），触发 `QUOTA_ROUTE_EXCEEDED`，新路由无法学习。
3. 中间链路 MTU 不一致导致 BGP Update 报文分片丢弃，会话反复震荡。

### 处置步骤
1. 执行工具 `tr-diag check-bgp --tr-id <TR_ID>`，确认 `bgp_neighbor_state` 与 `hold_timer` 配置。
2. 若为配额问题，执行 `tr-quota describe --tr-id <TR_ID>` 查看 `route_limit` 使用率；超限时提交配额工单扩容。
3. 若为链路 MTU 问题，将路径 MTU 统一为 1400，关闭 PMTU 黑洞。
4. 处置约束：调整 `hold_timer` 需对端同步修改，禁止单侧修改造成会话无法协商。

## CloudWAN 跨地域时延突增

### 告警说明
告警名 `CLOUDWAN_LATENCY_HIGH`，监控指标 `inter_region_rtt` 超过阈值。CloudWAN 通过骨干网连接多个地域，时延突增会直接影响跨地域数据库同步与音视频业务。

### 期望态
同地域 `inter_region_rtt` 应低于 5ms，跨地域（如 cn-beijing 到 cn-shanghai）应稳定在 30ms 以内，丢包率 `packet_loss_rate` 应低于 0.1%。

### 实际态
实际态为 `inter_region_rtt` 突增至 100ms 以上，`packet_loss_rate` 上升到 2% 以上，且 traceroute 显示流量绕行到非最优骨干节点。

### 常见根因
1. 骨干链路故障触发自动切换，流量绕行备用路径，路径变长。
2. CloudWAN 带宽包 `bandwidth_package` 打满，触发 `QUOTA_BANDWIDTH_EXCEEDED`，超出部分被限速丢包。
3. QoS 策略未对关键业务打标，拥塞时被降级。

### 处置步骤
1. 执行 `cloudwan-diag path --from <REGION_A> --to <REGION_B>` 查看当前路径与基线路径差异。
2. 执行 `cloudwan-metric show --package <PKG_ID>` 检查带宽包水位；打满时临时扩容带宽包并提交变更工单。
3. 为关键业务配置 QoS 高优先级标记 `dscp=46`。
4. 处置约束：骨干切换属于自动容灾行为，禁止人工强制回切未修复的故障链路。

## VPC 路由黑洞导致流量丢失

### 告警说明
告警名 `VPC_ROUTE_BLACKHOLE`。VPC 路由表中存在指向已删除或失效下一跳的路由条目，命中该条目的流量被静默丢弃。

### 期望态
VPC 路由表中每条路由的下一跳（如 NAT 网关、Transit Router 挂载、ECS 实例）都应处于 Available 状态，`route_status` 为 Active。

### 实际态
实际态为某条路由 `route_status` 变为 Blackhole，下一跳资源状态为 Deleted 或 Detached，目的网段不可达，`ping` 超时但无 ICMP 不可达返回。

### 常见根因
1. 作为下一跳的 ECS 实例被释放，但自定义路由未被清理。
2. Transit Router 挂载被解绑（Detach），指向该挂载的路由变为黑洞。
3. NAT 网关被删除后重建，ID 变化导致旧路由失效。

### 处置步骤
1. 执行 `vpc-route list --vpc-id <VPC_ID> --status blackhole` 定位所有黑洞路由。
2. 对每条黑洞路由，确认目标下一跳资源是否需要重建；需要则重建并更新路由指向新资源 ID。
3. 不再需要的路由直接删除，避免误导流量。
4. 处置约束：修改生产 VPC 路由表前必须确认目的网段无正在承载的关键流量，变更需走审批。

## 专线 BGP 收敛慢导致主备切换超时

### 告警说明
告警名 `PHYSICAL_CONN_FAILOVER_SLOW`。物理专线采用主备双线接入，主线故障时应快速切换到备线，切换超时会造成业务分钟级中断。

### 期望态
主线故障后，BGP 应在 `bfd_detect_time`（默认 150ms）内感知，并在 3 秒内完成路由收敛切换到备线，业务流量无感知或秒级抖动。

### 实际态
实际态为主线故障后切换耗时超过 30 秒，期间 `packet_loss_rate` 达到 100%，根因通常是 BFD 未启用，仅依赖 BGP `hold_timer`（默认 180 秒）超时才感知故障。

### 常见根因
1. 专线未启用 BFD 快速检测，故障感知依赖 BGP hold timer 超时。
2. 备线 BGP 通告的路由优先级 `local_pref` 配置错误，切换后路由未生效。
3. 主备线共用同一物理光缆或机房，未做真正物理隔离，同时故障。

### 处置步骤
1. 执行 `dc-diag check-bfd --conn-id <CONN_ID>` 确认 BFD 是否启用及 `bfd_detect_time`。
2. 未启用 BFD 时，为主备会话启用 BFD，检测间隔设为 200ms、乘数 3。
3. 校验备线 `local_pref` 高于主线故障后的兜底值，确保切换后路由可用。
4. 处置约束：启用 BFD 需主备两端同时配置，参数需一致，否则 BFD 会话无法建立。
